## Decisions the packet left to me

**Pinned to `@v1.0.0`, not `@v1`.** Both were permitted. The moving tag would let what is
denied change here with no commit in this repository, which is the thing the Boundary's
"do not change what is denied" protects. A denylist update should be a deliberate one-line
bump of `config/cost-guard-action.txt`.

**The pull-request comment step keeps its `continue-on-error`, and the contract check
allows it by line number rather than file-wide.** `platform-azure` could forbid
`continue-on-error` anywhere in its guarded-plan workflow because it has no comment step.
This repository has one, and it predates the packet — a comment that fails to post is not
a plan that went unguarded, so failing the job over it would be wrong, and deleting the
comment would be drift. `check-ci-contract.sh` therefore extracts the "Cost guard" step's
own block and forbids an excuse there, then walks every `continue-on-error` in the file by
line number and requires it fall inside the comment step. Case 2 below proves the scoping
is not a loophole.

**The infra READMEs were updated in the same commit.** `infra/oidc/README.md` and
`infra/state/README.md` both documented `tofu show -json … | ../../scripts/cost-guard.sh
/dev/stdin`. Deleting the script without touching them would leave two documented commands
pointing at a file that no longer exists. They now render the plan to a file and, in the
OIDC one, show how to run the pinned release's guard against that path by hand. `.gitignore`
gained `*.plan.json` so the rendered plan is not committable.

Undecidable is not softer than denied: both are non-zero and both fail the step. The same

**What I did not do, deliberately:** the five failing steps in that job carry
`continue-on-error` so the job can assert `outcome == failure`. A job that genuinely goes

demonstration would block every pull request forever. The real gate is `aws-plan.yml`,
where the guard step has no excuse and the contract check forbids one.

## 4. The contract check fails on an unguarded pipeline

Six ways to lose the gate, each seeded into the working tree and then restored:

```
1. the guard step is deleted
   Missing required contract text in .github/workflows/aws-plan.yml: uses: martcoca/cost-guard@v1.0.0
   exit=1
2. the guard step is excused with continue-on-error
   The "Cost guard" step in .github/workflows/aws-plan.yml carries continue-on-error.
   A guard that is allowed to fail is a workflow that looks guarded and is not.
   exit=1
3. the action is unpinned to a branch (@main)
   Workflow uses martcoca/cost-guard@main but the pin in config/cost-guard-action.txt is martcoca/cost-guard@v1.0.0.
   exit=1
4. the plan is piped into a re-vendored local guard
   Missing required contract text in .github/workflows/aws-plan.yml: >"$RUNNER_TEMP/tofu-plan.json" 2>"$RUNNER_TEMP/tofu-plan.err"
   exit=1
5. a local copy of the guard is committed again
   scripts/cost-guard.sh is back. The guard travels with the action; a local copy is the
   duplication that extracting it removed.
   exit=1
6. aws-identity.yml gains a pull_request trigger it did not have
   aws-identity.yml gained a pull_request trigger it did not have.
   exit=1

restored
   CI contract checks passed.
   exit=0
```

The check also asserts what a string match alone cannot: that the guard step follows the
plan step by line number, that no `tofu apply|destroy|import|taint|state rm|mv|push`
appears in the guarded-plan workflow, that no workflow applies infrastructure, and that
neither deleted file is present *or tracked*.

No workflow gained a `pull_request` trigger. `aws-plan.yml`, `cost-guard.yml` and
`guard.yml` already had one and keep it; `aws-identity.yml` and `auto-merge.yml` do not,
and case 6 is the assertion that keeps it that way. Every workflow that triggers on push
still accepts `workflow_dispatch` — `post-merge-workflows.sh check` passes and lists
`cost-guard.yml` and `guard.yml`.

## The local quirk, and how it was resolved

`aws-plan.yml` ran the guard with `working-directory: infra/oidc`, reaching back up with a
relative path and recovering two exit codes out of the shell after the fact. Both are gone:

- `tofu plan` keeps `working-directory: infra/oidc` and writes
  `$RUNNER_TEMP/tofu-plan.json` — an **absolute** path, because the next step is a `uses:`
  and a composite action does not inherit a step's `working-directory` the way a `run:`
  does. A path relative to `infra/oidc` would not resolve inside the action.
- The guard step is `uses: martcoca/cost-guard@v1.0.0` with
  `plan: ${{ runner.temp }}/tofu-plan.json`, and the job's exit code is the step's.

The plan step still sends `tofu plan` stderr to a file rather than the log, because this
repository is public and that stream can carry the state location.

## A finding about T01's interface, specific to this consumer

**The action exposes the verdict but not the denial detail.** `platform-azure` did not
need it. This repository posts the guard verdict as a pull-request comment, and the old
local pipeline captured the guard's stderr — `Denied resource: aws_nat_gateway.example
(NAT Gateway): ~$32/mo` — and put those lines in the comment body. The released action
writes that text to its own step summary and step log, but exposes only `verdict` and
`exit-code` as outputs, so a consumer cannot get the denied resource's name back out of
the step. The comment therefore now names the verdict and points at the run instead of
reprinting which resource was denied.

This is a real loss of information in the pull-request comment, not a loss of gating: the
job still fails, and the resource is still named in the job summary one click away. A
`denied` (or `detail`) output on the action would restore it for any consumer that reports
somewhere other than the job summary. Worth T05's attention; it is not worth reaching into
`cost-guard` from this packet.

## Notes for whoever does platform-gcp and T05

- **Do not blanket-forbid `continue-on-error` in the guarded-plan workflow if that workflow
  reports anywhere.** Azure could; this repository could not, because a pull-request
  comment step legitimately carries one. Scope the assertion to the guard step and then
  check the remaining occurrences by line number. A file-wide `grep -v` of the comment
  step's own text does *not* work: `continue-on-error: true` is the same string wherever it
  appears, so subtracting the comment step's lines deletes every occurrence and reports a
  clean file. Verified, not reasoned: with `continue-on-error` seeded on the *reporting*
  step of `aws-plan.yml`, the line-number check reports
  `continue-on-error at .github/workflows/aws-plan.yml:100 is outside the "Publish the
  guard verdict on the pull request" step` and exits 1, while the subtract-the-text version
  counts `0` occurrences outside the comment step and reports the file clean.
- **Prose costs you an hour if the contract check matches on literals.** `require_absent
  'cost-guard\.sh|/dev/stdin|PIPESTATUS'` matches the *comment* explaining why those are
  forbidden. Two of my first three failures were the check correctly rejecting my own
  explanation of it. Write the comment without the literal names and say why.
- **The pin file plus "every `uses:` equals it" is worth copying** — it is what makes "the
  version CI runs" and "the version we think it runs" the same string by construction.
- **The absolute-path fix is confirmed on a real runner, not just reasoned about.** The
  action received `plan: /home/runner/work/_temp/tofu-plan.json` from a step that does not
  inherit the plan step's `working-directory`. If your plan step also runs in a
  subdirectory, `${{ runner.temp }}/…` is what works.
- The traps the packet named — the plan file path, `uses:` not inheriting
  `working-directory`, and the `continue-on-error` that removes the gate — are all real and
  all bit in that order. The Azure evidence file is why this packet knew them in advance;
  that is the argument for writing this section rather than skipping it.
