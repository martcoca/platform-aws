# 0010-E02-T03 — platform-aws reports a stale pin

This repository now says, in its own CI, whether the cost guard it enforces is the current
one. Two places, on purpose:

- **`aws-plan.yml`**, beside the guard step, `if: always()`, `fail-on-stale: false`. Reports
  on every pull request, blocks nothing.
- **`cost-guard-freshness.yml`**, a daily `17 6 * * *` schedule, `fail-on-stale: true`. Goes
  red and stays red while the pin is behind. Never runs on a pull request, so it cannot
  block anyone's work.

**The pin was already current** (`v1.0.2`, which is `martcoca/cost-guard`'s latest release
and the same commit as its `main`, `b2721b4`), so it is unchanged by this packet.

## What a stale pin looks like here

This is the thing to recognise. On a pull request, in the `Cost guard freshness` step of
`Real AWS plan guarded for cost`:

```
cost-guard freshness: behind — pinned to v1.0.1 (93fada3); the current release is v1.0.2 (b2721b4)
##[warning]pinned to v1.0.1 (93fada3); the current release is v1.0.2 (b2721b4)
```

The step **succeeds**, the job stays green, and the job summary gains a "The cost guard pin
is behind" section listing the three steps to clear it. On the scheduled run the same
verdict fails the job instead.

`current` looks like `::notice title=cost-guard is current::pinned to the current release
v1.0.2`. `unknown` looks like `::warning title=cost-guard freshness unknown::the current
release could not be determined`, and is never dressed up as `current`.

### 5. The schedule

`17 6 * * *` — daily at 06:17 UTC. Off the hour deliberately: GitHub delays scheduled runs
that pile up at `:00`, and a job whose entire value is "it ran when nobody asked" should not
be queued behind everyone else's midnight cron.

When the pin is stale it reports `behind`, writes a summary naming the current release and
the three steps needed to adopt it, and **fails**. It stays red every day until the pin is
bumped. It cannot block a pull request: it has no `pull_request` trigger (the contract check
asserts that), and a failed run never satisfies auto-merge's
`workflow_run.conclusion == 'success'` condition.

## Findings about T01's interface

### The freshness action cannot be pinned backwards

The natural way to demonstrate staleness is to pin the whole repository one release back.
That does not work, and the failure mode is bad:

```
Set up job    failure
```

`freshness/` first exists in the commit released as **v1.0.2**. At `v1.0.1` the path does
not exist, so `uses: martcoca/cost-guard/freshness@v1.0.1` cannot be resolved and the job
dies at *Set up job*, before any step runs — including the guard.

This matters beyond the demonstration. The guard and the freshness action share one version
namespace but not one lifetime, and this repository's contract check requires every `uses:`
to carry the pin's ref. **So rolling the pin back below v1.0.2 makes CI un-runnable rather
than merely old** — and a rollback is exactly the emergency where you least want that. A
consumer still on v1.0.0 or v1.0.1 cannot adopt freshness at all without bumping first.

Nothing in this repository can fix that; it is a property of how the sub-action is
versioned. Options for whoever owns it: keep a moving `@v1` for the freshness step only,
publish the freshness action separately, or state plainly that v1.0.2 is the floor for
consumers. The demonstration here was done instead with the **pin file** one release behind
and the `uses:` refs left at v1.0.2 — an inconsistent tree, which the contract check
correctly refused on that branch while the freshness step still reported `behind`.

### A failed lookup can write a malformed step output

With a bad token rather than an unreachable host, `gh api` prints its JSON error body to
**stdout**, so the action's `resolve()` captures it. The status is still correctly
`unknown` — the safety property holds — but `$GITHUB_OUTPUT` receives 14 lines where the
contract is 6:

```
 1  status=unknown
 2  pinned-ref=v1.0.2
 3  pinned-commit={
 4    "message": "Bad credentials",
 5    "documentation_url": "https://docs.github.com/rest",
 6    "status": "401"
 7  }
 8  latest-release={
 9    "message": "Bad credentials",
...
14  detail=the current release could not be determined
```

Two problems. `pinned-commit` and `latest-release` are documented as empty when they could
not be determined, and instead carry an error body a consumer might render into a summary
or a comment. And a multi-line value written to `$GITHUB_OUTPUT` without a heredoc delimiter
is malformed: the runner parses each line on its own, so an error body containing a
`key=value` line can set an output nobody declared. Line 6 above is `"status": "401"` —
quoted and indented, so it does not collide with the real `status` output today, but the
shape of the hazard is there.

It is out of this packet's boundary to fix (`cost-guard` is not mine to change) and it is
why demonstration 3 above uses an unreachable host rather than a bad token: that path keeps
the outputs clean and empty. A one-line `2>/dev/null` becoming `>/dev/null 2>&1` on the
`resolve()` call, or quoting the writes with a delimiter, would close it.

### The pin now appears in three places, not two

`config/cost-guard-action.txt`, the guard's `uses:`, and the freshness `uses:`. The `pin:`
*input* is fed from the file, so that part is fine — but `uses:` cannot take an expression,
so the version is still a literal in every workflow. The scanner change below is what keeps
them honest; without it the third place was invisible.

## The contract check's pin scanner was blind to the freshness action

Worth stating separately, because it is a defect this packet introduced the conditions for
and then found:

The scanner matched `^[[:space:]]*uses:[[:space:]]*[A-Za-z0-9._-]+/cost-guard@…$` — `@`
straight after `cost-guard`. `martcoca/cost-guard/freshness@anything` matches none of it. So
the sub-action could have sat on `@main`, or on any older release, and the check would have
reported every use as matching the pin. Demonstrated against the pre-change script with the
freshness action moved to v1.0.1 and the guard left at v1.0.2:

```
--- PRE-CHANGE scanner (origin/main)
CI contract checks passed.                                                          exit=0
--- THIS BRANCH
Workflow uses martcoca/cost-guard/freshness@v1.0.1 but the pin in
config/cost-guard-action.txt is martcoca/cost-guard@v1.0.2.                         exit=1
```

The pattern now admits `owner/repo/sub@ref` and compares repository and ref separately
rather than the whole string, and a use count requires at least one freshness use to exist
at all.

## A defect in my own self-test, found by the demonstration

The drift case originally sedded the freshness ref to `@v1.0.1`. That is a no-op whenever
the repository is *itself* pinned to v1.0.1 — the "drifted" file comes out identical to the
real one, the check passes it, and the self-test then fails with `expected exit 1, got 0`.
It does not wave anything through; it breaks the build for the wrong reason while asserting
nothing about drift.

Found by pinning this repository to v1.0.1 for demonstration 2, which is a better argument
for running that demonstration than the packet's own. The sentinel `@v0.0.0-not-the-pin`
cannot collide with a real release. Verified afterwards against a tree consistently pinned
to v1.0.1: the self-test still reports five refusals.

## Decisions the packet left to me

**`fail-on-stale` false on pull requests, true on the schedule** — as the packet suggested
and T01 recommended. A release nobody has picked up yet must not turn unrelated pull
requests red, and a warning nobody is obliged to act on is not a control. The schedule is
where it stops being ignorable.

**A separate workflow for the schedule, rather than a `schedule:` trigger on
`aws-plan.yml`.** The plan workflow needs AWS OIDC and does a real `tofu plan`; running that
daily to ask a version question would be a cloud round-trip for a question that needs none,
and would give the freshness signal a dependency on AWS credentials being healthy. The new
workflow touches no plan, no verdict and no credential, and the contract check asserts it
stays that way (`require_absent 'tofu|aws-actions/configure-aws-credentials'`).

**The broken-lookup demonstration is a standing CI job, not a one-off.** Done-when asked me
to show a denied plan still failing and a clean plan still passing while the lookup is
broken. Doing that once by hand proves it about one commit; a job proves it about every
commit, and it is the property most likely to be quietly lost if someone later "simplifies"
the guard and freshness into one step.

**Both steps read the pin from the file**, per T01's guidance, and the contract check
asserts `pin: ${{ steps.pin.outputs.pin }}` in all three workflows rather than a literal.

## What I could not verify

- **That the scheduled run actually fires.** `cost-guard-freshness.yml` has never run on a
  schedule, because a `schedule:` trigger only becomes active once the workflow is on the
  default branch. The first firing is after this merges, on the next 06:17 UTC. What is
  verified is the workflow's content and that the same action, inputs and pin-reading step
  work on a runner in `aws-plan.yml`; what is not verified is GitHub's scheduler picking it
  up. **Whoever reads this next should check that a run exists** — a scheduled workflow that
  silently never fires is the same invisible failure this packet exists to remove, one level
  up.
- **A `behind` verdict on the scheduled path specifically.** Demonstration 2 exercised
  `behind` through `aws-plan.yml` with `fail-on-stale: false`. That the same verdict *fails*
  the step under `fail-on-stale: true` was verified locally against the released script
  (`exit=1`, "failing the step because fail-on-stale is set"), not on a runner.
- **The `unknown` path on the scheduled workflow.** Same reasoning: verified in
  `cost-guard.yml`'s job and locally, not on the scheduled workflow itself.
- **Nothing was applied.** No cloud mutation. The only cloud contact was the `tofu plan`
  that every pull request already runs.

is not the session's to clear.

## Notes for platform-azure and platform-gcp

- **v1.0.2 is the floor.** You cannot adopt the freshness action on a pin below it, and you
  cannot roll back below it once adopted without CI failing at *Set up job*. Bump first.
- **Extend your pin scanner before you add the step**, not after. If yours matches
  `cost-guard@`, it will silently ignore `cost-guard/freshness@` and report a clean contract
  while the sub-action sits on any ref at all.
- **Use an unreachable `GH_HOST`, not a bad token**, to simulate a failed lookup. Both give
  `unknown`, but the bad-token path writes a malformed multi-line step output.
- **Put the schedule in its own workflow** if your plan workflow needs cloud credentials.
- **Do not pin your drift fixtures to a real release number.** Use a sentinel; a real one
  becomes a no-op the day you pin to it.
