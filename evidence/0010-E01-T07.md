# 0010-E01-T07 — the AWS contract check is anchored

Every structural assertion in `scripts/check-ci-contract.sh` now requires a real YAML line.
Two negative fixtures are committed under `tests/fixtures/contract/`, and the check
demonstrates its own refusals on every run, so CI exercises them without a workflow change.

No workflow, no pin, no denylist, and nothing about what is denied was touched. `git diff
--name-only` against `main` lists `scripts/check-ci-contract.sh`, the two fixtures, the
packet files, and this file.

## The briefing was right about the defect and wrong about which fixture reproduces it

The packet's headline shape — the guard step deleted and replaced by a comment naming it —
**already failed** this repository's pre-change check. Not by anchoring: `step_block()`
finds the guard step with awk line *equality* (`$0 == want`), and a commented-out header is
not equal to a real one. That was an accidental anchor, and it caught the obvious case.

The defect is real and just as severe; it needed one turn of the screw to reach:

| compromise | pre-change check |
|---|---|
| guard step deleted, replaced by a comment naming every line it had | **exit 1** — "No "Cost guard" step … The plan is unguarded." |
| `- name: Cost guard` kept as a real line, its body commented out, step now runs `echo "guard temporarily disabled"` | **exit 0 — "CI contract checks passed."** |

The second file has no guard on it at all. `step_block` opens a block on the real header,
and every assertion inside it was `grep -Fq`, satisfied by the commented-out body. The
whole-file `require`s were satisfied by the same comments, and the ordering grep
(`grep -n "uses: ${pin}"`) matched the commented `uses:` line, so even the plan-then-guard
sequence appeared to hold.

**Both fixtures are committed**, not just the one that reproduces. The first is now a
regression guard for the accidental anchor: if `step_block` is ever loosened to a substring
match, that fixture starts passing and the self-test fails.

This is worth passing on. A repository whose check has one accidental anchor can look
immune to the reported defect while being wide open one step away. The question to ask is
not "does the reported fixture fail?" but "what is the *most* commented-out this file can
be and still pass?"

## What was anchored, what was not, and why

**Anchored** with `^[[:space:]]*<regex>[[:space:]]*$` — assertions that a line exists. A
comment begins with `#` after its indent and cannot match:

- in `aws-plan.yml`: the plan redirect, `uses: <pin>`, `plan: ${{ runner.temp }}/…`,
  `id: cost-guard`, `GUARD_OUTCOME:`, `GUARD_VERDICT:`,
  `[[ "$GUARD_OUTCOME" == "success" ]] || exit 1`, and all four
  `echo "<verdict>" >>"$GITHUB_STEP_SUMMARY"` lines;
- the same three assertions scoped inside the guard step's block, via a new
  `require_line_in`;
- in `cost-guard.yml`: `permissions:`, `contents: read`, `uses: <pin>`, and the five
  `assert '…' '…' "$VAR"` lines;
- the `uses:` pin scanner, and both line-number greps behind the plan-then-guard ordering.

Each anchored pattern was checked to match at least one real, non-comment line — an
over-escaped regex that silently matches nothing would otherwise hide behind a green run.
Every one matched exactly one line except `echo "undecidable" >>"$GITHUB_STEP_SUMMARY"`,
which matches two (lines 119 and 136), and `uses: <pin>` in `cost-guard.yml`, which matches
seven.

**Left as fixed-string, deliberately:**

1. **`require 'tofu plan -input=false -no-color -json'`.** That command ends in a `\`
   continuation, so it is half a line and cannot be matched whole. It is not left bare: the
   ordering grep below it is anchored to the *start* of a real line beginning with the same
   command, and exits if there is none. A comment cannot satisfy that one.
2. **Every rejection** — `require_absent`, the `continue-on-error` walk, the `tofu
   apply|destroy|…` greps. For a forbidden thing, matching a comment too is *fail-closed*:
   a commented-out pipeline is at worst a false refusal, and a false refusal is the safe
   direction for a gate. The one place where a false refusal was actually costing something
   is the `uses:` scanner, which is a required-shape assertion, and it is anchored.
3. **The trigger checks** (`^[[:space:]]*pull_request:` inside the `on:` block) were already
   anchored to the start of a line in both directions, and are unchanged.

The `require` helper is kept and now carries a comment saying it is for text-anywhere
assertions only; exactly one caller remains.

## One fix beyond anchoring, and why it is in this change

`plan_line`, `guard_line` and `comment_start` are assigned from `grep … | head | cut`.
Under `set -euo pipefail`, a grep that matches nothing fails the pipeline and `set -e`
kills the script **at the assignment** — before the `if` below can print what was wrong.
Found by tracing a run that exited 1 with no output at all. Each now ends `|| true`, so the
existing message is reachable.

It still failed closed before, so this is not a hole. It is in this change because the
packet's Check asks the failing check to *say* the line must be real, and a check that can
refuse silently undermines that. Three characters, one comment, no assertion weakened.

## The negative fixtures run in CI without a workflow change

The Boundary says `scripts/check-ci-contract.sh` and its tests only, and Done-when says the
fixture must be exercised by CI. Both hold at once only if the demonstration lives inside
the check itself, which `guard.yml` already invokes. So it does:

`check-ci-contract.sh` ends by building a throwaway tree in `mktemp -d` — a copy of itself,
the five workflows, the pin file — installing each fixture as `aws-plan.yml` and re-running
itself there with `--no-selftest`. **The real working tree is never modified**; a gate that
edits the repository to test itself is a worse problem than the one it is testing for.
`git status` after a run is clean.

The alternative was a separate `scripts/test-contract-check.sh` plus a new step in
`guard.yml`. If the chief-of-staff prefers that split, it is a small follow-up — but it
needs a workflow edit, and this packet's Boundary forbade one.

Five cases run, and the two passing ones matter as much as the three failing: a self-test
that refuses everything is not a self-test that discriminates.

```
guard step replaced by a comment       expect exit 1 + the anchoring message
guard step body commented out          expect exit 1 + the anchoring message
a real unpinned uses: line             expect exit 1 + "but the pin in"
a commented-out unpinned uses:         expect exit 0
the real workflow, unmodified          expect exit 0
```

The two `uses:` cases are derived from the real workflow by `sed` at run time rather than
committed, so they cannot go stale.

### The self-test discriminates — verified, not assumed

A self-test that cannot fail is decoration. With `require_line`'s anchors removed from a
copy of the finished script, the self-test refuses to certify:

```
Self-test "guard step replaced by a comment": output did not mention It must be a real YAML
line, not a mention of one in a comment.
No "Cost guard" step in .github/workflows/aws-plan.yml. The plan is unguarded.
exit=1
```

That is the message assertion earning its place: the case still *fails*, but for the old
accidental reason, and the self-test says so rather than accepting the exit code.

## What I could not verify

- **The CI run itself, at the time of writing.** Everything above is local. The runner adds
  nothing new here — the check is pure shell over files in the checkout and does no network
  or cloud work — but the actual run is on the pull request, not in this file.
- **That the anchored set is complete.** I anchored every assertion I could identify as
  being about a line, and listed the exceptions with reasons. What I cannot show is that no
  assertion was missed. The self-test covers the guard step and the pin; an assertion about,
  say, `contents: read` in the demo workflow is anchored but has no fixture proving it.
- **`mktemp -d` behaviour on the runner.** The self-test assumes a writable temp directory
  and that `git ls-files` inside a non-repository fails quietly, which it does locally
  (macOS) and is expected to on Linux. If the self-test misbehaves in CI it will fail the
  job, not pass it.
- **Nothing was applied, planned, or authenticated.** No cloud call of any kind.

## Notes for whoever anchors the remaining check, and for T05

- **Do not trust a green run of the reported fixture.** Ask what the *most* commented-out
  version of the file is that still passes. Here the reported shape was already refused and
  a one-line variant walked straight through.
- **An accidental anchor is worth making intentional.** `step_block`'s awk line equality was
  doing real work by luck. It now has a committed fixture pinning that behaviour, so
  loosening it to a substring match fails CI instead of silently reopening the hole.
- **Anchor required things; leave forbidden things unanchored.** For a rejection, matching a
  comment too is fail-closed. The single exception is a scanner that reports a *required
  shape* as violated — the pin scanner — where a comment caused a false refusal.
- **Watch `set -euo pipefail` around `$(grep … | head | cut)`.** A no-match kills the script
  at the assignment, and the message you carefully wrote below it never prints. It fails
  closed, so no alarm goes off; you find it only by tracing.
- **A self-test needs passing cases too.** Three refusals prove it can refuse; the two
  acceptances prove it is not simply refusing everything.
